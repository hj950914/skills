# 测试与完成前审查

## 测试规范

- 使用项目已有的 JUnit 5、Mockito、AssertJ 或其他测试体系。
- 优先为核心业务规则编写快速、独立的单元测试。
- 按项目惯例使用 MockMvc、WebTestClient 或测试切片测试 Controller。
- 让 MyBatis/JPA 数据访问测试覆盖关键 SQL、映射和边界条件。
- 只在确有必要时为集成测试加载完整 Spring 上下文。
- 对外部数据库、Redis、Kafka 等场景沿用项目已有的 Testcontainers 方案。
- 修复 Bug 时优先补充能够复现问题的回归测试。
- 让测试名称表达场景和期望结果。
- 保持测试相互独立，不依赖执行顺序和共享脏数据。
- 不为通过测试而删除有效断言或降低验证强度。

## 完成前检查

对所有新增和修改内容执行适用检查：

1. 是否遵循现有模块、包结构和相邻代码惯例。
2. Controller 是否包含业务逻辑或直接调用 Mapper。
3. 方法是否过长、嵌套过深、参数过多或职责混杂。
4. 是否存在含义不明确的魔法值。
5. 是否存在模糊命名、重复代码，是否缺少必要的简短注释，或存在无意义、过期的注释。
6. 是否存在空指针风险、返回 `null` 集合或滥用 `Optional`。
7. 是否吞异常、重复记录异常或泄露敏感信息。
8. 日志是否使用参数化写法，级别是否合理。
9. 事务范围是否过大，是否包含耗时远程调用。
10. SQL 是否存在注入风险、N+1、无条件更新或查询过多字段。
11. 是否需要新增或更新测试，Bug 修复是否有回归测试。
12. 是否执行项目已有的格式化、编译、静态检查和测试命令。

## 验证与处理

- 优先运行与改动最相关的快速测试，再运行仓库要求的完整检查。
- 若实现任务中的检查发现了本次改动范围内的问题，直接修复并重新验证。
- 若任务仅要求审查、解释或诊断，报告问题及依据，不自行修改代码。
- 记录未运行的检查及原因，区分“未运行”“失败”和“通过”。
