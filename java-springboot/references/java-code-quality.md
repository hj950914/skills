## 方法与复杂度

将以下数字作为代码审查触发阈值，而不是机械性的行业强制标准：

- 方法超过约 40 行时，检查是否需要拆分。
- 方法超过约 60 行时，通常提取职责明确的私有方法或对象。
- 条件或循环嵌套超过 3 层时，优先使用卫语句、提前返回或职责拆分。
- 方法参数超过 5 个时，检查是否应使用参数对象。
- 让一个方法只处理一个主要职责，并保持相近的抽象层级。
- 不为满足行数阈值进行无意义拆分。
- 对复杂分支考虑策略、枚举行为、状态机或领域对象，同时避免过度设计。
- 避免重复代码；仅当逻辑稳定且语义一致时提取公共方法。

## 注释与文档

- 为新增和修改的代码补充必要、简短且紧邻实现的注释，不提交只有实现而缺少关键说明的业务代码。
- 至少为新增业务类提供一句职责说明，并为公共 API、关键业务流程、复杂分支、边界条件、第三方协议约束、不直观实现和重要设计决策提供注释。
- 优先解释代码的意图、业务语义、约束和“为什么这样做”，不要逐行翻译实现。
- 沿用项目现有的注释语言和格式；项目没有明确约定时，对类和公共方法使用简洁 Javadoc，对局部关键逻辑使用简短行注释或块注释。
- 不为简单 getter、setter 或语义清晰的私有方法添加无意义注释。
- 修改行为后同步更新相关注释和文档，禁止保留与实现不一致的过期注释。
- 删除大段被注释掉的旧代码，将历史交给版本控制系统。
- 让 TODO 说明待办原因和后续动作，不只写模糊的 `TODO`。
- 让 Javadoc 保持简洁，只说明职责、参数约束、返回语义和必要异常。

## 命名

- 类和接口使用含义明确的名词，方法使用描述行为的动词。
- 布尔值和布尔方法优先使用 `is`、`has`、`can`、`should`、`supports` 等自然命名。
- 集合变量通常使用复数。
- 避免 `data`、`info`、`obj`、`temp`、`handle`、`process` 等含义模糊的名字。
- 让 DTO、Command、Query、Response、Entity、DO、VO 等后缀遵循项目已有语义，不为同一概念混用多个后缀。
- 不使用无意义缩写；允许行业通用缩写。

## 常量、枚举与魔法值

- 不在业务逻辑中保留含义不明确的数字和字符串字面量。
- 对封闭的业务状态优先使用枚举，而不是整数或字符串状态码。
- 将环境相关、可调整的值放入配置。
- 对有单位的值使用 `Duration`、`DataSize` 或领域值对象。
- 将可复用固定值放在其所属领域附近。
- 禁止创建包含无关常量的 `GlobalConstants`、`CommonConstants` 垃圾桶。
- `0`、`1`、`-1`、空字符串等字面量在语义明显时可以保留，不机械提取。
- 让常量名称表达业务含义，而不是简单复述值。

### 常量归属与作用域

- 将常量放在能够表达其语义的最小作用域内，不为“统一管理”提前提升可见性。
- 仅被一个类使用时，保留为该类的 `private static final` 常量。
- 被同一领域或协议的多个类使用时，放入对应领域、适配器或客户端附近；确有复用价值时再提取职责单一的包级常量类，优先保持 package-private。
- 将 HTTP 字段名、第三方协议参数、消息头和请求类型等实现细节放在负责组装请求的 Client、Adapter 或 Request Builder 中，不让应用服务感知底层协议。
- 仅在语义稳定且确实需要跨模块共享时暴露公共常量；禁止仅因字符串重复就创建全局常量。
- 区分“协议字段名”和“实际配置值”：固定字段名可作为常量，实际地址、账号、密钥、超时和环境差异值应进入强类型配置。
- 让名称区分参数名与参数值，例如 `PARAM_GRANT_TYPE` 和 `GRANT_TYPE_PASSWORD`；即使字面量相同，语义不同也可保留为不同常量。

## 空值、集合与 Optional

- 在系统边界校验外部输入。
- 不返回 `null` 集合，返回空集合。
- 不将 `Optional` 用作实体字段、DTO 字段或方法参数。
- 当“结果可能不存在”属于正常语义时，可将 `Optional` 用作返回类型。
- 不用 `Optional` 替代简单清晰的空值判断。
- 使用包装类型时检查自动拆箱导致的空指针。
- 处理集合时考虑空集合、重复元素、顺序和并发修改。
- Stream 难以阅读时使用普通循环。
- 禁止在 `map`、`filter`、`peek` 中加入隐藏副作用。

## 异常处理

- 对预期的业务失败使用项目统一的业务异常和错误码。
- 不使用异常代替正常流程控制，不静默吞掉异常。
- 捕获异常后保留原始异常作为 cause。
- 除系统边界外，避免直接捕获 `Exception` 或 `Throwable`。
- 让异常信息包含必要上下文，但不得包含密码、Token、私钥等敏感信息。
- 不在多个层级重复记录同一个异常。
- 只有能够恢复、转换或补充上下文时才捕获异常。

## 日志

- 使用 SLF4J。项目已使用 Lombok 时可使用 `@Slf4j`，否则使用标准 Logger 声明。
- 使用参数化日志，禁止字符串拼接：

```java
log.info("Processing userId={}, orderId={}", userId, orderId);
```

- 不记录密码、Token、Cookie、验证码、私钥和完整身份证等敏感数据。
- 在日志中包含排障所需的业务标识和请求标识。
- 根据场景选择 DEBUG、INFO、WARN、ERROR，避免滥用 ERROR。
- 避免在高频循环中打印大量日志。
- 不同时打印异常消息和完整异常而导致重复输出。
- 不使用 `System.out.println` 代替日志框架。
